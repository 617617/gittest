# Traceable Execution Review

**Extracted:** 2026-04-20
**Updated:** 2026-05-08 (v4 - decoupled project-hardcoded paths; ruler.md is now optional and discoverable)
**Context:** Post-execution code review for plans generated by the `traceable-plan` skill. Reads git commit info to locate and verify plan artifacts.

## Dirty Worktree Checkpoint Gate

Whenever this skill or its calling protocol requires a clean worktree, first
inspect `git status --short --branch` in the repository containing the reviewed
commit or plan directory. If the worktree is dirty, create exactly one
full-repository checkpoint commit before continuing:

```powershell
git add -A
git commit -m "chore(worktree): checkpoint before traceable-review"
git status --short --branch
```

Continue only if the follow-up status is clean. If the commit fails or the
worktree remains dirty, stop with:

```text
TRACEABLE_REVIEW_BLOCKED_DIRTY_AFTER_CHECKPOINT
```

Do not treat a dirty worktree as an immediate blocker until this checkpoint
attempt has been made. This gate does not change boundary-check semantics:
`CLEAN`, `CREEP`, and `BREACH` still refer to plan scope, not merely git
cleanliness.

## Output Language Rule (MANDATORY)

ALL artifacts produced by this skill MUST be **English-only with ASCII punctuation**. This applies to:

- The post-execution review report (top of conversation output and any persisted markdown)
- The Review Capsule output (if used)
- Review Trail entries appended to stage `evidence.md`
- Findings tables, severity labels, and architectural-health notes

Rules:
1. **English-only**. Prose, headings, table cells, severity labels -- all English.
2. **ASCII quotes only**. Straight `"` and `'`; never curly variants.
3. **No Unicode punctuation**. Use `--`, `...`, `-` instead of em-dash / en-dash / ellipsis / bullet.

The conversation with the user may be in any language; this rule applies only to files and embedded report blocks written to disk or to commit messages.

## Pre-Read: Framework Boundary Principles (Optional)

**BEFORE starting any review step**, if the change touches OPS / orchestration / external framework integration:

If the project has a framework-boundary principles document, read it first. Look in this order:

1. `docs/framework-boundary/ruler.md`
2. `docs/architecture/boundaries.md`
3. Any path declared in the plan's `00_master.md` under a `boundary_doc:` key

Such a document typically defines stances applicable to ANY external framework (Temporal / Dramatiq / LLM Gateway / PydanticAI / etc.). Core stance:

> External frameworks are outer infrastructure, NOT the business semantics brain.

**If no such document exists OR the review target does NOT touch orchestration / framework boundaries -> SKIP this pre-read entirely.**

## Runtime Infrastructure Context Gate

Before classifying any finding, use this gate when the reviewed diff, evidence,
tests, or failure output touches runtime infrastructure integration:
Redis/cache/throttle, Channels, Dramatiq, Temporal, DB connection/migrations,
workers, background jobs, Docker/compose, ports, env vars, CI/service topology,
or deployment settings.

Required checks:

1. Inspect the relevant runtime topology files before claiming a service, port,
   cache, worker, dependency, or environment is missing or wrong. Prefer:
   `docker-compose.yml`, `docker-compose.*.yml`, `.env.example`, deployment env
   docs, `dnd_backend/settings.py` or active settings modules, Dockerfiles or
   requirements files when dependencies matter, and focused infrastructure
   tests.
2. Classify each finding as exactly one primary type: code defect,
   environment/service defect, test-environment configuration defect, or
   product/architecture decision. Explain the file or command evidence for the
   classification.
3. Do not treat a Redis/cache/throttle/worker failure as a product code failure
   until compose/env/settings and test toggles or overrides have been checked.
4. Do not run DB-backed pytest commands in parallel. Run them serially or
   explicitly isolate their test databases.
5. If a review report asserts "Docker is missing", "Redis is unavailable",
   "the port is wrong", or "cache config is absent", it must cite the local file
   evidence that supports that assertion.

### Mandatory Review Questions (boundary doc S3)

Every diff touching OPS / business boundaries MUST answer:

1. **What was replaced**: Which old entry point / runtime shell / bypass path is being replaced?
2. **What was preserved**: Which semantic layers are explicitly preserved?
3. **What was frozen**: Which old paths are frozen with no new call sites?
4. **What is the truth source**: Who owns runtime truth? Which are just projections?
5. **What is the exit condition**: What is the clear exit criterion for old paths?

Any diff that cannot answer all 5 = architectural risk.

### Red Flags (boundary doc S4)

- Framework code (workflow / activity / agent / gateway) becoming business brain
- Old path still growing + new path also growing (dual growth)
- Business entity re-assuming runtime decision logic
- Second state store / trace system / gate / policy layer / writer appearing
- Change touching DAG + post-DAG + apply + policy + job state + API without clear contract reason

### Review Checklist Shortcut (boundary doc S9.4)

```
[ ] Entry paths reduced?
[ ] Business logic stays in spine modules?
[ ] No parallel writer / state store / trace system?
[ ] Offline tests still runnable?
[ ] Truth source + projection clearly separated?
[ ] Old path has exit condition?
[ ] No old logic moved into framework package?
```

All 7 boxes required for PR PASS.

## Pre-Check: Is This a Traceable Plan?

**BEFORE activating this skill, run this check:**

```bash
# Check if recent commits contain the structured template markers
git log --all --grep="Stage:" --grep="Scope:" --grep="Evidence:" --oneline -n 10
```

**Activation criteria (ALL must be true):**
1. Git log contains commits with `Stage:` field in message body
2. Git log contains commits with `Scope:` field pointing to a plan path
3. Those plan directories actually exist in the repo

Accepted plan roots mirror the repository commit-message validator. Generic traceable-plan commits normally use `.claude/plan/`; Blue-K commits normally use `docs/mian-k/`.

**If ANY criterion fails -> DO NOT activate this skill.** Fall back to standard `/code-review` or `/review-pr` instead. This skill only works for plans generated by `traceable-plan`.

## When to Use

Trigger when (after pre-check passes):
- User says "review the plan execution", "review commits", "verify the changes"
- A traceable-plan has been executed and needs post-hoc review
- User invokes `/code-review` or `/review-pr` on commits from a structured plan
- `stage-loop` Phase 3 calls this skill against the just-produced commit

## Overview

This skill is the **review half** of the closed loop. It reads structured git commit messages to locate plan documents, then cross-references actual code changes against the plan scope.

```
Git commits (structured messages)
  -> Parse commit fields (stage, scope, evidence, plan refs)
    -> Read plan documents
      -> Read actual code diffs
        -> Cross-reference changes vs scope
          -> Produce structured review report
```

## Step 1: Extract Execution Info from Git

### 1.1 Find the Commit Range

```bash
# Find all plan-related commits (they contain "Stage:" in message body)
git log --all --grep="Stage:" --oneline

# Or find commits since a specific point
git log <start-ref>..HEAD --oneline

# Or find commits by plan name
git log --all --grep="<PLAN_NAME>" --oneline
```

### 1.2 Parse Structured Commit Messages

Each commit message follows the template from `traceable-plan`:

```
<type>: <summary>

Stage: <stage number and name>
Scope: <relative path to stage scope.md>
Evidence: <relative path to stage evidence.md>

Plan refs:
- <path to stage card .md>
- <path to source requirement .md>#<section>

Changed runtime files:
- <path>: <description>

Tests:
- <test file path>: <what it proves>

Acceptance verdict: <PASS | WARN>
```

**Extract these fields from each commit:**

```bash
# Get full commit message body
git log <hash> -1 --format="%B"

# Get changed files list
git diff-tree --no-commit-id --name-only -r <hash>

# Get full diff
git diff <hash>^..<hash>

# Get diff stat (summary)
git diff <hash>^..<hash> --stat
```

### 1.3 Build the Execution Map

From parsed commits, build a map:

```
Commit: 2a9bee0
  Stage: 02 - NL edit alignment
  Scope: <plan-root>/.../02_step2.../scope.md
  Evidence: <plan-root>/.../02_step2.../evidence.md
  Plan refs: [...]
  Changed files: [nl_edit_service.py, graph_ops_apply.py]
  Tests: [tests_nl_edit_service.py: update_node adoption]
  Verdict: PASS
```

## Step 2: Read Plan Documents

For each commit, read the referenced plan documents:

1. **Stage card** (`<stage-NN>_<name>.md`) - what was the stage supposed to do?
2. **Stage scope** (`<stage-NN>_<name>/scope.md`) - what are the acceptance checks?
3. **Stage evidence** (`<stage-NN>_<name>/evidence.md`) - what was claimed?
4. **Root scope** (`scope.md`) - what commit protocol was specified?
5. **Master** (`00_master.md`) - what cross-stage rules apply?
6. **Canonical memory file** (AGENTS.md / CLAUDE.md / CONTEXT.md at repo root) - what shared vocabulary was agreed upon?

## Step 3: Boundary-First Review

**Review order matters.** Check boundaries BEFORE diving into code semantics.

### 3.0 Boundary Check (FIRST)

Check the file boundary before any other review:

```bash
# Get actual changed files
git diff-tree --no-commit-id --name-only -r <hash>

# Compare against EXECUTE.md's Allowed Files list
# If "Changed runtime files" exists in commit message, cross-check against git diff-tree
```

**Boundary checklist:**

- [ ] All changed files are in the stage's Allowed Files list
- [ ] No unrelated files were modified
- [ ] No frozen / Do Not Touch files were touched
- [ ] Generated files or ignored files are explicitly recorded
- [ ] **Read Anchor authenticity audit**: if EXECUTE.md cited `<file>:<symbol>` anchors, `audit_trace.md` should contain the planner's verification entries (one line per anchor with grep result). Missing entries = MEDIUM finding (planner skipped Step 7 item 9). Anchors that grep cannot find but were cited = HIGH finding (anchor was fictional).

**If boundary check fails -> mark stage `BLOCKED` before deeper review.** Do not proceed to semantic review until boundary is clean.

### 3.1 Evidence Verification (SECOND)

Before any substantive review, verify the evidence is tool-grounded:

1. **Test claims**: does evidence.md include actual pytest command output? Or just "46 passed" with no command? Mark `[UNVERIFIED]` if no command output.
2. **Behavioral anchors**: were they written BEFORE the diff (from Rule 3), or reconstructed after? Evidence written after-the-fact is weaker but acceptable if accurate.
3. **Changed files**: if the commit message includes "Changed runtime files", compare it with `git diff-tree` output. If the field is omitted, use `git diff-tree` as the source of truth.
4. **Acceptance verdict**: does the claimed verdict (PASS/WARN) match the actual test output? A "PASS" with failing tests = CRITICAL finding.

Any claim that cannot be traced to tool output gets marked `[UNVERIFIED]` in the review report. Multiple `[UNVERIFIED]` items are a strong fabrication-risk signal -- the reviewer must weigh whether the missing evidence is unavoidable (environment, tool gap, sandbox limit) or symptomatic of fabrication, and assign WARN/BLOCK by judgment. Three or more `[UNVERIFIED]` items is a heuristic for when to look harder, NOT an automatic verdict; the reviewer can accept a higher count when the executor has documented why each one was unavoidable, and conversely escalate even one `[UNVERIFIED]` when the missing evidence covers a load-bearing claim.

### 3.2 Drift Signal Detection (THIRD)

Check for drift signals that indicate the execution went off track:

| Drift Signal | Severity | Action |
|--------------|----------|--------|
| Implementation requires files outside Allowed set | BLOCK | Escalate to main agent |
| Current repo behavior contradicts capsule assumptions | BLOCK | Re-plan needed |
| Acceptance checks cannot be verified with available tools | BLOCK | Evidence incomplete |
| Tests fail for reasons not explained in stage scope | BLOCK | Root cause unknown |
| Executor had to infer missing product/architecture decisions | WARN | Capsule was incomplete |
| Evidence claims PASS but tests show failures | CRITICAL | Fabricated evidence |
| Behavioral anchor contradicts actual code change | HIGH | Semantic drift |

**If any BLOCK-level drift signal is detected -> STOP and report.** Do not continue reviewing until the blocker is resolved.

## Step 4: Semantic Review (After Boundary Passes)

### 4.1 System-Level Check (from Matt Pocock's zoom-out)

Before detailed per-function review, verify at system level:
1. Do changes flow in the correct dependency direction (core <- orchestration <- API)?
2. Any cross-layer leaks (e.g., orchestration logic in a core module)?
3. Any new dependency between previously independent modules?
4. If this change were reverted, would anything else break? (coupling check)
5. **Vertical slice verification**: Does each commit deliver a thin, end-to-end verifiable change? Or is it a horizontal layer sweep? Horizontal commits are acceptable only if explicitly flagged in the stage card.

### 4.2 Feedback Loop Check (from Matt Pocock's diagnose)

For commits that fix bugs or diagnose issues, verify the feedback loop discipline. Apply the full hypothesis-enumeration check only to Strict-tier work or diagnosis-heavy commits (incident, flaky failure, unknown root cause, ambiguous bug). For straightforward bug fixes with an obvious failing test, require the signal and regression-test checks but do not require 3-5 hypotheses.

1. **Was a fast, deterministic pass/fail signal built BEFORE the fix?**
   - Failing test, curl script, CLI invocation, or headless browser script
   - If no signal was built, flag as HIGH - the fix was applied blind
2. **Was the loop iterated on?** (made faster, sharper, more deterministic)
3. **For Strict-tier or diagnosis-heavy commits only:** were 3-5 falsifiable hypotheses generated before testing any?
4. **Was the regression test written BEFORE the fix?**
5. **If no correct test seam exists, was that flagged as an architecture finding?**

Feedback loop quality scale:
- **Excellent**: deterministic loop < 5s, hypotheses ranked and falsified
- **Good**: loop exists, some iteration, fix follows regression test
- **Poor**: no loop, fix-first approach, no hypothesis enumeration
- **Missing**: fix committed with no verification signal at all

### 4.3 Scope Creep Check

For each commit, compare **actual changed files** against **plan scope**:

```bash
# Actual changed files
git diff-tree --no-commit-id --name-only -r <hash>

# Compare against plan scope's allow list
# If "Changed runtime files" exists, cross-check it against git diff-tree.
# If omitted, use git diff-tree as the changed-file source of truth.
```

Rules:
- Every changed file MUST trace to an acceptance check in the stage scope.
- If the commit includes "Changed runtime files", every listed file MUST match `git diff-tree`; mismatches are evidence drift.
- If "Changed runtime files" is omitted, reconstruct the changed-file list from `git diff-tree`.
- Any file outside stage scope = scope creep = MUST flag as HIGH.

### 4.4 Semantic Drift Check (Behavioral Equivalence)

For each function that was modified, verify:

```
BEFORE: <fn> does X, Y, Z. Key invariant: <what must not change>
CHANGE: modify <lines> to achieve <stage goal>
AFTER:  <fn> does X, Y, Z' (only Z changed). Key invariant preserved.
```

Read the evidence.md's "Behavioral Anchor Record" if present. If not present, reconstruct from git diff.

Key checks:
- [ ] Function signature unchanged (or change is explicitly in scope)
- [ ] Return type/value unchanged (or change is explicitly in scope)
- [ ] Exception paths unchanged (or change is explicitly in scope)
- [ ] Side effects unchanged beyond stage scope
- [ ] Called-by contracts still satisfied

### 4.5 Hardcoding and Vocabulary Audit

Scan all added/changed lines for:

| Pattern | What to Check |
|---------|--------------|
| String literals in logic | Must match constants/enums defined elsewhere |
| Magic numbers | Must be explained or match existing constants |
| Module path strings | Must match actual file paths |
| Node/edge type strings | Must match `models.py` or `nlp_constants.py` definitions |
| Operation type strings | Must match `graph_ops_models.py` OpType |
| Vocabulary violations | If canonical memory (AGENTS.md / CLAUDE.md / CONTEXT.md) defines a Shared Vocabulary section, verify new code uses agreed terms (e.g., entity_type vs node_type) |

```bash
# Quick scan for potential hardcoding
git diff <hash>^..<hash> | grep "^+" | grep -E '"[a-z_]+"' | grep -v "^+++"
```

### 4.6 Contract Consistency Check

For each changed function that has callers:

1. Find all callers: `grep -rn "function_name(" --include="*.py"`
2. Verify each caller's expectations still match:
   - Argument count and types
   - Return value shape
   - Exception types
   - Side effects

### 4.7 Test Verification

```bash
# Run all tests mentioned in commit messages
python -m pytest <test files listed in commit> -v

# Check overall test count matches claimed
# E.g., "46 passed, 0 failed" from evidence
```

## Step 5: Produce Review Report

### 5.0 Executor Load Check (retrospective)

The planner should have validated this at generation time (Step 7). Verify it actually happened:

- Did `HANDOFF_execute.md` point to only the current stage's `EXECUTE.md`? If not, flag as HIGH - executor was reading audit-layer docs.
- **Was the Global Context section populated with substance** (Plan-level Goal / Architecture Invariant / Stage Sequence Position prev-this-next / System-level Non-Goals / Plan-level Accept)? Missing or hand-waving fields = MEDIUM plan-quality finding -- the executor was forced into local-only reasoning, which is the failure mode the loop exists to prevent (transferring reviewer-AI's global perspective to executor-AI is intent #1; this section is the carrier). Length is NOT a finding on its own; ~150 lines is a yardstick, not a cap.
- **Was the Execution Discipline preamble actually injected by stage-loop?** Check the Phase 2 prompt log if available. If the preamble is missing AND the evidence shows symptoms (paraphrased stdout, missing behavioral anchors, fabricated PASS verdicts), flag as HIGH plan-or-orchestrator quality finding -- the anti-laziness floor was not enforced.
- Did `evidence.md` contain facts rather than essays? If the executor wrote paragraphs of interpretation, the plan did not make expectations clear enough.

This is a **plan quality** finding, not an execution quality finding. It tells the planner to do better next time.

## Step 6: Optional Architecture Health Check

If 3+ plans have been completed without an architecture review, or the review conclusion is PASS:

1. Scan recently modified modules for "deepening opportunities":
   - Modules with wide interfaces but thin logic -> suggest deeper abstractions
   - Mixed concerns in single files -> suggest separation
   - Scattered magic numbers/strings -> suggest centralized config
2. **Deletion test** (from Matt Pocock's improve-codebase-architecture):
   - For each candidate module, ask: "If I delete this module, what happens to the complexity?"
   - If complexity vanishes -> the module was a pass-through (candidate for removal/merge)
   - If complexity reappears across N callers -> the module was earning its keep (candidate for deepening)
   - One adapter = hypothetical seam. Two adapters = real seam worth abstracting
3. Check module dependency health:
   ```bash
   grep -rn "^from\|^import" <changed files> | sort | uniq -c | sort -rn | head -20
   ```
4. Record findings as ADRs in `docs/adr/`
5. If findings affect an active plan, note it in the review report

This is optional and does not affect the PASS/WARN/BLOCK verdict.

## Review Capsule Template (Optional)

For complex multi-stage plans, generate a review capsule per stage to focus the review:

```markdown
# Review Capsule: <stage-id>

## Objective
Review whether the executor completed this stage capsule honestly and inside scope.

## Inputs
- Execution capsule: <path to EXECUTE.md>
- Changed files: <from git diff-tree>
- Diff: <from git diff>
- Evidence: <path to evidence.md>

## Allowed Boundary
- Allowed changed files: <list from EXECUTE.md>
- Frozen files: <list from Do Not Touch>
- Known non-goals: <from stage card>

## Required Checks
- [ ] Diff only touches allowed files
- [ ] Evidence records exact commands and outcomes
- [ ] Acceptance checks are satisfied or explicitly blocked
- [ ] No command failure is treated as a pass
- [ ] No missing context was guessed through

## Escalate If
- The fix requires files outside the boundary
- Current code contradicts the capsule's stated assumptions
- The executor changed behavior not covered by acceptance checks
- Evidence is missing for a claimed pass

## Output
Verdict: PASS / WARN / BLOCK

Findings:
- severity, file:line, issue, required narrow fix
```

**When to use**: Strict-tier plans, or when a stage has complex cross-file dependencies. The capsule focuses the reviewer on the specific stage scope, preventing scope creep in the review itself.
