# Blue K Plan Audit

Audit `blue-k-planner` output before any package is executed by
`stage-loop-auto`.

Default paths:

```text
docs/blue
docs/mian-k
docs/past-k
```

This skill is the review half of the `blue-k-planner` loop:

```text
blue-k-planner creates K package
  -> blue-k-plan-audit reviews every executable leaf package
    -> stage-loop-auto executes only packages that passed audit
```

`blue-k-git-baton-testkit/references/ai-chat-contract.md`:

2. **Wrong-window input must refuse.** If this chat does not match the
   `ChatTarget` printed by the latest `bk sync`, do not acquire a lease,
   edit files, or call any Blue-K skill; reprint the correct
   `ChatTarget` / `ChatCommand` and stop.
3. **Finalize with a fixed closing line.** After one safe assignment, push
   the work branch and coordination branch atomically, write the next
   holder into `BATON.yaml`, and end the reply with exactly
   `Done. Now run: bk sync`. Do not chain into the next package, lane, or
   assignment.

For `/bk takeover`, no destructive recovery may begin before the human types
`yes, abandon` in this chat.

## Core Rules

- Audit documents only. Never edit source code.
- Persisted artifacts must be English-only with ASCII punctuation.
- Use one subagent per minimal executable package. Subagent review is mandatory.
  If subagents cannot be spawned, stop with `BLUE_K_AUDIT_BLOCKED_NO_SUBAGENT`.
- Each subagent gets only the package-local context it needs, plus a small origin
  capsule. Do not give it the entire blueprint.
- The auditor must know where the package came from, why it exists, what it must
  accomplish, what it depends on, and what it must not do.
- Each package review must be source-grounded. Slight context over-inclusion is
  allowed when it prevents the reviewer from guessing.
- Each package review must verify the five boundary questions:
  `what was replaced`, `what was preserved`, `what was frozen`, `truth source`,
  and `exit condition`.
- Each package review must verify any package-local BDD/TDD marker and test
  organization marker before allowing `stage-loop-auto` execution.
- Do not execute packages. Do not advance or archive the K lock.

No direct main-agent substitute is allowed for package review.

## Minimal Executable Package

A minimal package is a directory that `stage-loop-auto` can execute by reading a
thin execution packet. It normally contains:

```text
00_master.md
PACKAGE_CHARTER.md
scope.md
audit_trace.md
HANDOFF_execute.md
HANDOFF_review.md
stage-01_<name>.md
PRE_REVIEW_REPORT.md
stage-01_<name>\
  scope.md
  evidence.md
  EXECUTE.md
```

For package sets, the set directory itself is not executable. The numbered
children are executable:

```text
main\PACKAGE_SET_INDEX.md
main\00_<package>\...
other\01_<branch_set>\PACKAGE_SET_INDEX.md
other\01_<branch_set>\00_<subpackage>\...
```

Reject loose packages as non-strict when they only contain:

```text
scope.md
evidence.md
EXECUTE.md
```

## Workflow

1. Inspect the K package root and lock files.
2. Load `PACKAGE_GENERATION_MAP.yaml` when present.
3. Load or reconstruct `AUDIT_MANIFEST.yaml`.
4. Discover every minimal executable package.
5. Verify each package has:
   - `PACKAGE_CHARTER.md`
   - `HANDOFF_execute.md`
   - `stage-01_*.md`
   - `stage-01_*\EXECUTE.md`
   - `stage-01_*\scope.md`
   - `stage-01_*\evidence.md`
   - `audit_trace.md`
   - BDD/TDD marker in the package docs when the assignment requires one
   - Test Placement Ledger when the package creates or edits tests
6. Verify each package maps to one assignment in
   `PACKAGE_GENERATION_MAP.yaml` unless the manifest marks the package as
   `inferred: true`.
7. Create or update `AUDIT_CONTEXT.md` for each executable package.
8. Spawn one pre-doc-review subagent per package.
9. Give each subagent only:
   - the package path;
   - that package's `AUDIT_CONTEXT.md`;
   - the package-local docs;
   - the package-local `PACKAGE_CHARTER.md`;
   - the matching `PACKAGE_GENERATION_MAP.yaml` assignment only;
   - directly referenced parent `PACKAGE_SET_INDEX.md` or `Kx_INDEX.md` snippets;
   - relevant lock/topology/source-charter snippets, not the entire blueprint;
   - relevant BDD/TDD marker and test organization snippets when referenced by
     the assignment or `AUDIT_CONTEXT.md`;
   - enough source paths, discovery commands, and package-local behavior notes
     to avoid guessing;
   - the instruction to use `$pre-doc-review`;
   - the instruction to read relevant source code before final findings;
   - the instruction to verify the five boundary questions;
   - the instruction to verify required BDD/TDD and test placement before
     reporting stage-loop-auto readiness;
   - the instruction to write the package `PRE_REVIEW_REPORT.md`.
10. After each subagent returns, read the package `PRE_REVIEW_REPORT.md`,
   changed package docs, and package `audit_trace.md`.
11. Write the aggregate report:

```text
docs/mian-k\BLUE_K_PLAN_AUDIT_REPORT.md
```

12. Update `AUDIT_MANIFEST.yaml` package entries with review status.

## Subagent Prompt Shape

Use this shape for each package review subagent:

```text
Use $pre-doc-review.

Target package:
<package_path>

You are auditing exactly one minimal stage-loop-auto executable package produced
by blue-k-planner.

Read:
- <package_path>\AUDIT_CONTEXT.md
- matching PACKAGE_GENERATION_MAP.yaml assignment only
- <package_path>\PACKAGE_CHARTER.md
- <package_path>\HANDOFF_execute.md
- <package_path>\scope.md
- <package_path>\audit_trace.md
- <package_path>\stage-01_*.md
- <package_path>\stage-01_*\EXECUTE.md
- <package_path>\stage-01_*\scope.md
- <package_path>\stage-01_*\evidence.md
- <direct parent package-set index if provided>
- the relevant `BDD_TDD_MARKERS.md` snippet if named by the assignment or
  AUDIT_CONTEXT.md
- the relevant `TEST_ORGANIZATION_CHARTER.md` snippet if the package creates or
  edits tests
- source files and source discovery commands named by AUDIT_CONTEXT.md or the
  matching assignment

Do not read unrelated K packages unless a listed document requires escalation.
Do read enough relevant source code to verify package feasibility. If the named
source anchors are insufficient, read adjacent source files needed to avoid a
guess and mark that expansion in the review report.
Do not edit source code.

Review whether this package can be executed by stage-loop-auto without document
failure. Focus on broken paths, missing files, impossible dependencies,
scope/execute/evidence mismatch, charter injection failure, mismatch against the
generation assignment, stale origin context, and missing stop conditions.

Also verify that the package answers these five questions with source-grounded
or explicitly not-applicable answers:

1. What was replaced?
2. What was preserved?
3. What was frozen?
4. What is the truth source?
5. What is the exit condition?

Also verify package-local development discipline:

- If `bdd: required`, BDD scenarios must appear before implementation steps,
  name actors and observable outcomes, and map to test type or target test path.
- If `tdd: required`, EXECUTE.md must start with test, fixture, contract,
  golden-sample, or migration consistency work before implementation.
- If tests are created or edited, the package must declare test domain, target
  test paths, flat-test exception if any, and a first verification command.
- New tests must not be added as new root-level flat test files unless the
  package records an explicit exception.

Write:
<package_path>\PRE_REVIEW_REPORT.md

Fix WILL_FAIL documentation defects in this package only and record fixes in
<package_path>\audit_trace.md when present.

Return:
- verdict: PASS | WARN | BLOCK
- files changed
- WILL_FAIL findings remaining
- MAY_FAIL findings remaining
- source files inspected
- five questions verdict
- BDD/TDD verdict
- test organization verdict
- whether the package is stage-loop-auto ready
```

## Aggregate Verdict

Use these verdicts:

```text
PASS
WARN
BLOCK
NON_STRICT_PACKAGE
INCONSISTENT
BLUE_K_AUDIT_BLOCKED_NO_SUBAGENT
```

Rules:

- `PASS`: every executable package has a package review report and no remaining
  `WILL_FAIL`.
- `WARN`: no `WILL_FAIL`, but one or more `MAY_FAIL` or accepted non-blocking
  issues remain.
- `BLOCK`: at least one package has remaining `WILL_FAIL` or missing mandatory
  docs.
- `NON_STRICT_PACKAGE`: package shape is not compatible with the strict
  blue-k-planner contract.
- `INCONSISTENT`: manifest, lock, topology, or package docs disagree.
- `BLUE_K_AUDIT_BLOCKED_NO_SUBAGENT`: a required package review subagent could
  not be spawned.

## Stop Conditions

Stop before spawning reviews when:

- `mian-k` is missing.
- The target path is ambiguous.
- The current K cannot be identified.
- `ROADMAP_LOCK.yaml` or `K_STAGE_TOPOLOGY.md` is missing.
- No minimal executable package can be found.
- Manifest says a package exists but the directory is missing.
- A strict package has no matching `PACKAGE_GENERATION_MAP.yaml` assignment.
- A package has no `EXECUTE.md`.
- A package with `bdd: required` has no BDD section or no scenario-to-test
  mapping.
- A package with `tdd: required` starts with implementation before test,
  fixture, contract, golden-sample, or migration consistency work.
- A test-writing package has no declared test domain or target test paths.
- A required package review subagent cannot be spawned.

Report the exact blocker and do not edit unrelated files.
