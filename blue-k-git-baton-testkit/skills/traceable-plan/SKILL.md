# Traceable Plan Generation

**Extracted:** 2026-04-20
**Updated:** 2026-05-08 (v4 - tier philosophy clarified; shared vocabulary merged into canonical memory; thresholds parameterized; Stop Conditions de-duplicated)
**Context:** Multi-stage architecture refactoring that requires lossless traceability from requirement -> plan -> code -> review.

## Dirty Worktree Checkpoint Gate

Whenever this skill or a generated plan gate requires a clean worktree, first
inspect `git status --short --branch` in the repository containing the plan or
target code. If the worktree is dirty, create exactly one full-repository
checkpoint commit before continuing:

```powershell
git add -A
git commit -m "chore(worktree): checkpoint before traceable-plan"
git status --short --branch
```

Continue only if the follow-up status is clean. If the commit fails or the
worktree remains dirty, stop with:

```text
TRACEABLE_PLAN_BLOCKED_DIRTY_AFTER_CHECKPOINT
```

Do not treat a dirty worktree as an immediate blocker until this checkpoint
attempt has been made.

## When to Use

Trigger when:
- User requests a multi-stage refactoring or feature plan
- User says "generate plan", "create blueprint", "plan the implementation"
- Task involves 3+ stages or touches 5+ files
- `/multi-plan` or `/plan` is invoked for complex work

## Output Language & Encoding Rules

ALL generated plan documents MUST be:

1. **English-only**. All prose, headings, comments, evidence, commit messages, and audit entries must be in English. No exceptions. This applies to every file under the selected `<plan-root>/` including EXECUTE.md, scope.md, evidence.md, HANDOFF files, and stage cards.
2. **ASCII quotes only**. Use straight double quotes `"` (U+0022) and straight single quotes `'` (U+0027). Never use smart quote code points U+201C, U+201D, U+2018, or U+2019. These cause mojibake on non-UTF-8 terminals and waste tokens during debugging.
3. **No Unicode punctuation**. Avoid Unicode punctuation such as em dash (U+2014), en dash (U+2013), ellipsis (U+2026), and bullet (U+2022). Use `--`, `...`, and `-` instead.

**Why**: Non-UTF-8 terminals (Windows PowerShell with GBK codepage) mangle Unicode quotes into gibberish, wasting tokens and time to diagnose. English-only ensures all consumers (AI agents, codex, human reviewers) can parse documents without encoding issues.

## Plan Root Selection

Use the plan root that matches the workflow:

- Generic traceable-plan packages: `.claude/plan/`.
- Blue-K active packages generated by `blue-k-planner`: `docs/mian-k/`.

Use `<plan-root>` in templates when the root is workflow-dependent. Commit `Scope:` and `Evidence:` paths must use a root accepted by the repository commit-message validator.

## Tiers (Lite / Standard / Strict)

Not every plan needs the full ceremony. Pick a tier at plan creation time and record it in `00_master.md`.

**Tier philosophy**: Lite minimizes ceremony for low-risk work. Standard is the workhorse default. Strict is for **high-stakes outcomes** -- NOT "more paperwork". From the Strict column, pick the actually-relevant validations: don't apply migration metrics to a security incident, or hypothesis logs to a schema change. When in doubt, prefer outcome over ceremony.

| | Lite | Standard (default) | Strict |
|---|---|---|---|
| **When** | 1-2 stages, <5 files, low risk | 3-6 stages, multi-file refactoring | Data migration, architecture boundary, prod incident, security-sensitive |
| **GRILL** | Skip | Conditional (Step 0) | Mandatory if requirements ambiguous; skip if obvious (e.g., live incident with clear signal) |
| **Anti-drift protocol** | Rules 2, 4, 7 only | All 11 rules | All 11 rules; behavioral anchor table only when rename-heavy |
| **Commit template** | 4 required fields (Stage, Scope, Evidence, Tests) | 4 required + optional Changed files | All fields required |
| **Evidence template** | Status + Test Evidence only | Full template | Full template; add before/after inventory ONLY for migrations; add hypothesis log ONLY for diagnosis/incident |
| **Code review** | Self-review via `git diff` | code-reviewer agent | code-reviewer agent + second reviewer (security-reviewer for security; senior eng for architecture) |
| **Architecture health check** | Skip | After 3 plans | After every plan |
| **Feedback loop check** | Skip | For bug-fix commits only | Mandatory for incidents; standard otherwise |

**Tier selection rule of thumb**: when in doubt, use Standard. Only downgrade to Lite when the change is truly small (single-digit files, no architectural impact). Always upgrade to Strict when touching: data schema, auth/security, orchestration boundaries, or production incident response.

## Overview

This skill generates a structured plan that enforces a closed loop:

```
Phase 0: GRILL          (from Matt Pocock's grill-with-docs)
  -> Requirement clarification loop
  -> Update Shared Vocabulary in canonical memory (AGENTS.md / CLAUDE.md / CONTEXT.md)
  -> Record key decisions as ADRs
     -> Phase 1: PLAN GENERATION (this skill)
  -> Phase 2: doc-review (pre-execution gate)
    -> Phase 3: stage-loop execution
      -> Phase 4: traceable-review (post-execution code review)
        -> Phase 5: human acceptance
```

## Plan Directory Structure (Three-Layer Architecture)

Documents are split by **who reads them**, not just by topic:

| Layer | Reader | Principle |
|---|---|---|
| **Audit** | Planner, Reviewer | Thick. Full causal chain, all rules, all decisions. |
| **Execution** | Executor AI | Thin. Only what to do, where, and when to stop. |
| **Reference** | Anyone on demand | Shared Vocabulary in canonical memory, ADRs. Read when needed, not by default. |

```
<PLAN_NAME>/
  00_master.md          - AUDIT: Phase map, effort, all 11 rules, prior art
  scope.md              - AUDIT: Root router, commit protocol, verification
  audit_trace.md        - AUDIT: Append-only review/iteration log
  <stage-NN>_<name>.md  - AUDIT: Full stage card (8 sections)
  <stage-NN>_<name>/
    scope.md            - REFERENCE: Detailed acceptance checks
    evidence.md         - AUDIT: Filled during/after execution (facts only)
    EXECUTE.md          - EXECUTION: Thin execute packet (executor reads ONLY this)
  HANDOFF_execute.md    - Points to current stage's EXECUTE.md, nothing else
  HANDOFF_review.md     - Points to audit layer (reviewer reads thick docs)
```

Create this directory under the selected `<plan-root>`.

**Executor rule**: The executing AI reads ONLY `EXECUTE.md` (+ canonical memory file if vocabulary is needed). It does NOT read `00_master.md`, `scope.md`, or the full stage card. Those are audit-layer documents for the planner and reviewer.

**Package profile override**: Blue-K packages under `docs/mian-k/` may include package-local charters such as `PACKAGE_CHARTER.md`, `AUDIT_CONTEXT.md`, package indexes, and audit handoff files. Those files are allowed references only when explicitly listed by the package profile, `HANDOFF_execute.md`, or `EXECUTE.md`; they do not open the full audit layer to the executor.

**Planner responsibility**: When generating a plan, the planner must produce both the audit-layer documents AND the thin EXECUTE.md for each stage. The EXECUTE.md is a compressed, actionable extract - not a copy.

## Stage Card Template

Each stage card (`<stage-NN>_<name>.md`) MUST contain:

```markdown
# <NN> <Stage Name>

## Entry Condition
- What must be true before this stage starts
- Source refs to requirement document sections

## Exit Target
- What must be true after this stage completes

## In-Scope Concerns
- What this stage addresses

## Explicit Non-Goals
- What this stage deliberately does NOT address

## Recommended Sequencing
- Ordered steps within the stage

## Deliverables
- Concrete outputs expected

## Contribution To Final Acceptance
- How this stage contributes to the final gate

## Execution Mode
- `direct-code` | `tdd-mode` | `implementation-bridge` | `evidence-only`

## Source References
- Links back to requirement document sections
```

## Mandatory Plan Sections

### 1. Anti-Drift Protocol (in 00_master.md)

Every plan that involves code changes MUST include these rules:

```
### Rule 1: Read Before Write
Before modifying ANY function, read the entire function body first.
State in plain language what it currently does. If you cannot explain
the current behavior, you are not ready to modify it.

### Rule 2: Surgical Changes Only
Only change lines directly related to the stage scope:
- Do NOT reformat, re-indent, or "clean up" adjacent code
- Do NOT rename variables, add type hints, or improve comments outside scope
- Do NOT refactor "while you're here"

### Rule 3: Pre-Change Behavioral Anchor
For every function you modify, record BEFORE making changes:
  BEFORE: <fn> does X, Y, Z. Key invariant: <what must not change>
  CHANGE: modify <lines> to achieve <stage goal>
  AFTER:  <fn> does X, Y, Z' (only Z changed). Key invariant preserved.

### Rule 4: Diff Review Before Commit
After all code changes for a stage, run git diff and verify:
- No changes outside stage scope
- No ambiguous intent in any changed line
- All functions preserve stated invariants

### Rule 5: Test Before and After
1. Run existing tests BEFORE changes. Record baseline.
2. Make changes.
3. Run same tests AFTER. Any new failure is a regression.
4. Add new tests for new behavior only.

### Rule 6: No Unconnected Changes
Every line of code change must trace to a specific acceptance check.
Cannot point to which check -> do not make the change.

### Rule 7: Flag Uncertainty
If behavior is unclear or ambiguous: STOP and ask the user.
Do NOT pick one interpretation and proceed.

### Rule 8: Anti-Sycophancy
If the user's assumption contradicts the codebase, say so directly.
Do NOT silently accept a wrong premise to avoid friction.
"I see the code does X, not Y as you described" is always the right call.

### Rule 9: Tool-Grounded Evidence
All claims in evidence.md MUST be backed by real command output:
- Test results: must come from actual pytest run, not paraphrased
- File changes: must come from git diff, not memory
- Behavioral anchors: must come from reading the function body, not assumed
- If evidence cannot be tool-grounded, mark it `[UNVERIFIED]` - never fabricate
- A test result of "PASS" with no command output is `[UNVERIFIED]`

### Rule 10: Context Compaction Recovery
After a context window compaction or session restart:
1. Re-read the current stage's EXECUTE.md BEFORE continuing any work
2. Run `git diff --stat` to see current state vs last commit
3. Write one sentence in audit_trace: "Session resumed. State confirmed: <summary>"
4. If EXECUTE.md scope no longer matches current git state, STOP - escalate to audit layer (read scope.md + audit_trace.md) and re-plan if needed

### Rule 11: No Tool-Failure Tunneling
If a tool call (test run, file read, grep) fails or times out:
- Do NOT proceed as if it succeeded
- Do NOT assume the result based on prior knowledge
- Mark the dependent step as `[BLOCKED: tool failure]` and retry or ask the user
```

### 2. Execution Sequence Guard (in 00_master.md)

The plan MUST state:

```
## Mandatory Execution Order

For every direct-code stage:
1. **Stage revalidation gate**: executor re-reads the current stage's EXECUTE.md and runs `git diff --stat`. If EXECUTE.md no longer matches current git state, STOP and escalate to audit layer (read scope.md + audit_trace.md) and re-plan if needed.
2. Implement stage scope changes
3. Run tests (before + after comparison)
4. **Pre-commit code review** using the selected tier: Lite = self-review via `git diff`; Standard = code-reviewer agent; Strict = code-reviewer agent + second reviewer
5. Fix any CRITICAL or HIGH issues from review
6. Only THEN: git commit with structured message
7. Fill evidence.md (at minimum: status + test evidence, before commit)

NEVER commit without the tier-selected pre-commit review.
NEVER combine commits across stages.
```

**Review naming clarification**:
- **Pre-commit code review**: within-stage quality gate. Checks code quality, patterns, security. Happens before commit. Uses `code-reviewer` agent.
- **Traceable post-review**: cross-commit plan compliance review. Checks scope creep, behavioral equivalence, evidence accuracy. Happens after all stages complete (or at user request). Uses `traceable-review` skill.

These are two different reviews serving two different purposes. Apply them according to the selected tier: Lite may use self-review and defer traceable post-review unless requested; Standard and Strict should run both at their planned gates.

### 3. Structured Commit Template (in scope.md)

**Required fields** (all tiers):

```
<type>: <one-line summary>

Stage: <stage number and name>
Scope: <relative path to stage scope.md>
Evidence: <relative path to stage evidence.md>
Tests:
- <test file path>: <what it proves>
```

**Optional fields** (Standard and Strict):

```
Plan refs:
- <relative path to stage card .md>
- <relative path to source requirement .md>#<section>

Changed runtime files:
- <path>: <brief change description>

Acceptance verdict: <PASS | WARN>
```

`Changed runtime files` is optional because it can be derived from `git diff-tree`. If omitted, the reviewer will use git to reconstruct it.

### 4. Evidence Template (per stage)

**Executor writes facts. Reviewer interprets facts. Planner owns narrative.**

The executor fills ONLY the fact-based section. The reviewer may add the behavioral matrix and audit sections.

**Executor fills (all tiers):**

```markdown
# Stage <NN> Evidence

## Facts

### Commands run
For EACH command, fill ALL three lines. Empty stdout = `[UNVERIFIED]`. NEVER paraphrase.

- Command: `<exact command line>`
  Stdout (raw, paste exactly between fences):
  ```
  <paste tool output verbatim - if empty, write [UNVERIFIED: no output captured]>
  ```
  Result: PASS / FAIL / [UNVERIFIED]

### Behavioral anchors (one block per modified function)
- BEFORE: `<fn>` does X, Y, Z. Invariant: <what must not change>
  CHANGE: <lines> to achieve <stage goal>
  AFTER:  `<fn>` does X, Y, Z'. Invariant preserved: YES / NO

### Changed files
- <file>: <one-line what changed>

### Acceptance result
PASS / BLOCKED / [UNVERIFIED]

### Blockers (if any)
- <description>
```

**Anti-fabrication rule**: A "PASS" with empty or paraphrased stdout is treated as `[UNVERIFIED]` by the reviewer and counts as a fabrication risk. When multiple `[UNVERIFIED]` items appear in one stage, the reviewer must weigh whether the missing evidence is unavoidable (environmental tool gap, sandbox limit) or symptomatic of fabrication, and assign WARN/BLOCK by judgment. There is NO automatic-downgrade count -- three or more is a strong signal for the reviewer to look harder, not a hard cap that fires verdicts on its own. If a stage genuinely needs to ship with several `[UNVERIFIED]` items, the executor should record WHY each one is unavoidable in evidence.md, and the reviewer can accept it as a documented exception.

**Reviewer may add (Standard and Strict):**

```markdown
## Reviewer Notes
- **Behavioral anchors:** (reconstructed from git diff, not executor claims)
- **Scope compliance:** CLEAN / CREEP (<details if CREEP>)
- **Test verification:** <re-run results>
```

**Planner may add (Strict only):**

```markdown
## Before-vs-After Inventory
| Metric | Before | After | Delta |
|--------|--------|-------|-------|
```

## Plan Generation Steps

### Step 0: Grill Session (from Matt Pocock's grill-with-docs) - CONDITIONAL

**ONLY activate when requirements are genuinely ambiguous.** Skip if:
- A scope.md with clear Exit Targets already exists
- The user provides explicit, detailed requirements with clear boundaries
- The task is a continuation of an existing plan (evidence.md present)

**When to activate** (any of these):
- User provides a vague one-liner ("fix the performance issue")
- Requirements conflict with existing architecture
- Domain terms are ambiguous and not in canonical memory (AGENTS.md / CLAUDE.md / CONTEXT.md)
- Multiple valid interpretations exist for the same requirement

When activated, run a requirement clarification loop:

```
1. Read the requirement source
2. Run a grilling loop (ONE QUESTION AT A TIME):
   a. Ask ONE clarifying question - wait for answer before proceeding
   b. Provide your recommended answer alongside the question
   c. If the question can be answered by exploring the codebase, EXPLORE instead of asking
   d. For each answer, ask "what if that fails?" or "what happens at the boundary?"
   e. Only move to the next question after the current one is fully resolved
   f. Repeat until no new decision branches emerge
3. Update Shared Vocabulary in canonical memory (see Step 9 below)
4. Record key decisions as ADRs in docs/adr/
```

Grilling MUST cover:
- **Happy path vs error path**: What should happen when things go wrong?
- **Boundary conditions**: What's the smallest change? What's the largest reasonable change?
- **Naming ambiguity**: Does the requirement use domain terms that map to specific code concepts?
- **Backward compatibility**: What existing behavior MUST NOT change?
- **Testability**: How will you verify each piece of the change?

One-at-a-time discipline: NEVER batch 5-10 questions in one message. Each question is a turn. This ensures dependencies between decisions are resolved in order, not assumed.

### Step 1: Read the requirement source
Understand the full problem before structuring.

### Step 2: Identify stages
Each should have one clear intent: freeze gate, direct repair, guardrail, classification, acceptance.

**Vertical slicing rule** (from Matt Pocock's `to-issues`):
- Prefer stages that are **end-to-end verifiable** - a thin cut through all relevant layers (schema -> logic -> API -> tests)
- Avoid "horizontal stages" that touch only one layer across many features (e.g., "update all models")
- Each completed stage should be demoable or verifiable on its own
- When a stage is inherently horizontal (e.g., config migration), explicitly flag it and explain why vertical slicing isn't feasible

**Granularity heuristic**: prefer many thin stages over few thick ones. A stage that touches 10+ files is probably two stages.

### Step 3: Assign ownership
Every named surface/concern must have exactly one downstream stage owner.

### Step 4: Set entry/exit conditions
Stages must be sequentially defensible.

### Step 5: Estimate effort
Rough signals prevent stages from looking deceptively similar in size.

### Step 6: Reference prior art
Link to existing patterns (e.g. R01-R04 equivalents in this project).

### Step 7: Generate HANDOFF files and validate executor load
Both execute and review handoffs.

**Executor load validation** (MUST pass before plan is handed off):
1. EXECUTE.md is concise enough that the executor will actually read it? Treat ~150 lines as a useful yardstick (fits in roughly 3K tokens, leaves room for code work) -- it is NOT a hard cap. If a stage's EXECUTE.md is bloating past that, **prefer splitting the stage first**. If splitting genuinely does not work (one indivisible contract surface, irreducible step list), keep the longer EXECUTE.md and record the reason in `00_master.md` so reviewers know it was deliberate. Note: the Execution Discipline 4 rules are no longer embedded in EXECUTE.md (they are runtime-injected by stage-loop), so the budget freed by their removal goes to Global Context, not to filler.
2. **Global Context section is populated with substance, not placeholders**. All 5 fields filled: Plan-level Goal (2-3 sentences of user-facing outcome, not "modify file X"); Architecture Invariant (the system-level line not to cross); Stage Sequence Position (prev stage delivered / this stage's job / next stage will -- one line each); System-level Non-Goals (at least one bullet of "what would silently break the plan if quietly done here"); Plan-level Accept (1-2 lines of whole-plan success criterion). The planner pulls this from the audit-layer Stage Card's "Contribution To Final Acceptance" + "Source References" + 00_master.md -- it is a compression for the executor, not a copy. If a field is empty or hand-waving, the executor will fall back to local-only thinking and the loop's intent #1 (transferring reviewer-AI's global perspective to executor-AI) is broken at this packet.
2. HANDOFF_execute.md points to ONLY EXECUTE.md (+ optional canonical memory file)? No 00_master.md, no scope.md, no stage card.
3. EXECUTE.md has Allowed Files list? Executor must know what NOT to touch.
4. EXECUTE.md has Stop Conditions? Executor must know when to escalate.
5. Evidence section in EXECUTE.md asks for facts (commands, files, result) not essays (interpretations, narratives)?
6. **Lossless check**: Every acceptance check in stage scope.md appears in EXECUTE.md, or is explicitly marked "Reviewer-only" with a one-line reason. No scope.md check may be silently dropped.
7. Every Allowed File in EXECUTE.md maps to a planned concern in the stage card. No phantom files.
8. **Current State boundary check**: Current State section ONLY mentions files in Allowed Files or Read Anchors. If it mentions files outside these lists, the executor cannot verify this information and may make wrong assumptions.
9. **Read Anchor authenticity check**: For every `<file>:<symbol>` form anchor in EXECUTE.md, the planner MUST verify the location actually exists in the current repo BEFORE handing off:
   - File exists: Read tool returns content (not "file does not exist")
   - Symbol exists: `grep -n "<symbol>" <file>` returns at least one match
   - Record verification command + result in audit_trace.md (one line per anchor)
   - If an anchor cannot be verified, EITHER fix the anchor OR remove it and add a Stop Condition explaining what context is missing
   - Rationale: a fictional anchor forces the executor into a STOP loop or, worse, silent guessing. Catching it at generation time costs one grep; catching it at execution time costs a stage rollback.

If any check fails, fix the EXECUTE.md before proceeding. This is a generation-time gate, not a review-time check.

### Step 8: Write audit_trace.md
Initialize with first entry.

### Step 9: Maintain Shared Vocabulary in Canonical Memory

Use the project's existing canonical memory file -- do NOT create a parallel CONTEXT.md alongside it. Priority order:

1. `AGENTS.md` (Codex and other AI agent setups) -- add a `## Shared Vocabulary` section
2. `CLAUDE.md` (Claude Code projects) -- same section
3. `CONTEXT.md` at repo root -- only if neither AGENTS.md nor CLAUDE.md exists

When starting a new plan, read whichever canonical file exists. If the plan introduces new domain terms or resolves a naming ambiguity, **append** to the existing canonical file under `## Shared Vocabulary`. Do NOT create per-plan copies.

```markdown
## Shared Vocabulary

| Term | Definition | Code Location |
|------|-----------|---------------|
| entity_type | Pydantic schema field name for KG node classification | schemas.py |
| node_type | Django ORM field name on KnowledgeNode | models.py KnowledgeNode |
| apply | Persist graph operations to database | graph_ops_apply.py |

## Hard-to-Explain Decisions

- Why entity_type vs node_type: Pydantic schemas predate the Django model, both names stuck
```

**Why merge with canonical memory**: A separate CONTEXT.md fragments the truth source. AGENTS.md / CLAUDE.md is commonly loaded into agent context; making vocabulary live there means it is actually read, not just nominally referenced.

**Maintenance**: Keep lean. Only vocabulary terms + critical naming decisions that have caused or could cause confusion. Archive stale entries periodically. Do not dump implementation details, long ADRs, or historical discussion -- those belong in code comments or `docs/adr/`.

### Step 10: Assign Execution Modes per Stage (from Matt Pocock's TDD)

Each stage card's `Execution Mode` field now supports `tdd-mode`:

```
direct-code: Standard implement -> test -> review -> commit cycle
tdd-mode:    Red -> Green -> Improve cycle (for pure functions / data transforms / rule engines)
             1. Write FAILING test
             2. MINIMAL code to pass test
             3. Refactor within scope
             ALL red/green/improve work is committed as ONE stage commit (not 3 micro-commits).
             The structured commit template is used once, after the full cycle completes.
implementation-bridge: Requires human decision point mid-stage
evidence-only: No code changes, only documentation/evidence
```

**When to use tdd-mode**: `pipeline_config`, `graph_ops_normalize`, `graph_ops_models`, `knowledge_graph` ORM primitives, `combat_engine`, `cost_ledger`, new utility functions.

**When to use direct-code**: Orchestration layer changes (side effects, external calls), integration with existing systems, large-scale file reorganizations.

**tdd-mode strict rules** (from Matt Pocock's TDD discipline):

1. **ONE TEST AT A TIME** - write one failing test, make it pass, then write the next. NEVER write all tests first then all code (horizontal slicing). This produces tests that test imagined behavior rather than real user-facing behavior.
2. **Tests verify behavior through public interfaces** - if renaming an internal function breaks a test, that test was wrong.
3. **Only enough code to pass the current test** - do not anticipate future tests.
4. **Never refactor while RED** - get to GREEN first, then refactor.
5. Each test should respond to what was learned from the previous cycle.
6. ALL red/green/improve work is committed as ONE stage commit (not 3 micro-commits).

### Step 11: Architecture Health Check Schedule (from Matt Pocock's improve-codebase-architecture)

Add to `00_master.md`:

```markdown
## Architecture Health Check

After every 3 completed plans OR every 2 weeks (whichever comes first):
1. Run architecture review on recently modified modules
2. Check for "deepening opportunities":
   - Shallow modules (wide interface, thin logic) -> deeper interfaces
   - Mixed concerns -> separate responsibilities
   - Scattered magic numbers -> centralized config
3. Apply the **deletion test** for each candidate module:
   - If deleting the module makes complexity vanish, it was a pass-through (good candidate for removal/merge)
   - If complexity reappears across N callers, the module was earning its keep (good candidate for deepening)
4. Record findings as ADRs in docs/adr/
5. If findings affect an active plan, update that plan's scope.md

This is NOT a stage in any plan - it is a cross-plan maintenance practice.
```

## EXECUTE.md Template (Thin Execute Packet)

Each stage gets its own `EXECUTE.md`. Keep it thin enough that the executor will actually read it -- the working yardstick is roughly 80-150 lines (this fits in roughly 3K tokens and leaves room for code work in the executor's context). It is **not** a hard cap.

If a stage's EXECUTE.md is bloating past that:
1. **Prefer splitting the stage first.** Most "I need 250 lines" cases are actually two stages glued together.
2. If splitting genuinely does not work (one indivisible contract surface, irreducible step list, regulated single-commit boundary), keep the longer EXECUTE.md and record the reason in `00_master.md` so reviewers know it was a deliberate keep, not drift. There is no `execute_md_max_lines: <N>` override -- the planner just writes one or two sentences explaining why this particular stage cannot be made thinner.

**Isolation Rules (embedded in every EXECUTE.md):**
- Read ONLY this file + Allowed Files + Read Anchors
- Do NOT read: 00_master.md, scope.md, stage cards, other stages' evidence, audit_trace.md
- If you need more context than provided, STOP and report - do not explore on your own
- For Blue-K packages, package-local charters explicitly listed in the execute packet are part of the Read Anchors, not a permission to inspect unrelated packages or blueprint files.

```markdown
# Stage <NN>: <Name> - Execute Packet

## Isolation Boundary
**READ ONLY:** This file + files listed in Allowed Files + files listed in Read Anchors.
**DO NOT READ:** 00_master.md, scope.md, stage cards, other stages' EXECUTE.md or evidence.md, audit_trace.md.

If you need context beyond what is provided, STOP and report missing context. Do NOT explore.

## Execution Discipline (Runtime-Injected, NOT Embedded Here)
The 4 anti-laziness rules (Read Before Write / Pre-Change Behavioral Anchor / Tool-Grounded Evidence / No Tool-Failure Tunneling) are injected as a SYSTEM PREAMBLE by the stage-loop orchestrator at execute time. They are deliberately NOT duplicated in this file -- the executor receives them via runtime injection and applies them throughout. If you are running this EXECUTE.md WITHOUT stage-loop (e.g., another orchestrator or a manual dispatch), load the discipline preamble manually before starting; otherwise anti-laziness floor is undefined and this stage's evidence becomes uninterpretable.

## Global Context (READ FIRST -- audit-layer perspective compressed for the executor)
This is the part that gives you the same global view the reviewer has. Read it before touching any local step. If any field below is empty or vague, STOP and ask the planner -- do NOT fall back to local-only reasoning.
   ```
